# CreditPulse PRD

## Scope

CreditPulse is a three-agent diligence-and-monitoring copilot for a fictionalized venture-debt borrower, Meridian SaaS Co. The product demonstrates how bounded agents can support private-credit monitoring without replacing deterministic calculations, policy gates, or human review.

## Agents and deterministic services

| Component | Role | Guardrail |
| --- | --- | --- |
| Extraction agent | Converts static source documents into cited JSON fields. | Every field must include a document and section/line citation. |
| Covenant monitor | Computes liquidity runway, ARR growth, net burn multiple, and NRR compliance. | Ratios are calculated in code; LLM annotations cannot override them. |
| Memo drafter | Produces cited monitoring prose. | Unsupported factual claims render as `[NEEDS REVIEW]`. |

`/ask` is **not** a fourth agent. It is a fixed, deterministic lookup index over the same extraction/covenant data the other three services already produce and cite — see §6. It never calls an LLM to determine a value and never guesses; a question outside its fixed lookup set returns an explicit not-available response instead of a generated answer.

`/simulate` is also **not** a new agent, and does not add a second covenant implementation. It constructs hypothetical monthly rows from scenario overrides and hands them to the exact same `covenants.monitor_covenants()` function `/covenants` uses for real history — every threshold, ratio formula, and breach rule comes from that one function. No LLM is involved.

## Venture-debt covenants

The prototype intentionally uses growth-stage lending terminology: ARR growth floor, minimum liquidity / cash runway, burn-to-growth cap, and net revenue retention floor. It avoids leveraged-loan metrics such as DSCR unless explicitly needed for context.

## Evaluation centerpiece

The evals dashboard should emphasize charts for:

- Extraction accuracy against ground truth.
- Covenant breach detection precision and recall.
- Memo hallucination rate from claim-to-source traceability.
- Regression across at least two prompt/model iterations.

## Sponsor & Founder Diligence module

A fourth pillar, added after the financial-covenant build — diligence on *who* is being lent to, not just the financials. Full spec, including the explicit sensitive-data framing rules, lives in `CreditPulse_Sponsor_Diligence_PRD.md`; see §6 below for the endpoint shapes. Three deterministic/bounded pieces, none a fifth "agent":

- **Founder profile extraction** (`founder_extraction.py`) — deterministic, cited parsing of `founder_bios.md`/`cap_table.md`, identical citation pattern to `extraction.py`.
- **Wealth signal estimator** (`wealth_estimator.py`) — a pure function, no LLM in the number: an estimated *range* (never a bare figure) from disclosed prior-exit proceeds and/or a finalized current cap table stake, with a confidence label and methodology note. The uncertainty band is confidence-linked, not flat: it widens proportionally to how many of the two possible components are actually disclosed (25% at full disclosure, 50% at partial), so a "low confidence" estimate reads as visibly wider, not just differently labeled at the same tightness. A founder with no usable disclosed data gets an explicit `insufficient_data: true` result, never a guess.
- **Network graph + concentration flag** (`investor_network.py`) — `investor_network.json` served as a structured passthrough; the concentration-risk flag is plain set intersection over `board_seat` edges, not an LLM judgment.
- **Adverse media classification** (`adverse_media.py`) — cited extraction plus LLM-assisted classification (live Claude call when available, deterministic keyword fallback otherwise, same live/fallback pattern as the memo drafter) into `resolved_immaterial` vs `ongoing_ambiguous`. A structural keyword safety gate runs on every classification afterward and forces `ongoing_ambiguous` whenever a record's own text contains unresolved language — an ambiguous item is never auto-classified as clean, enforced in code rather than left to prompting alone.

Eval ground truth for this module (`data/ground_truth/wealth_estimate_answer_key.json`, `data/ground_truth/adverse_media_answer_key.json`) was authored independently of the module's own code — the wealth answer key from a hand computation over the raw disclosed source figures, the adverse-media answer key from an independent read of each record's text — specifically to avoid repeating the MAC-clause ground-truth tautology (see `field_accuracy_answer_key.json`'s `mac_style_interpretive_field` caveat).


## 6. Backend JSON contract

The Lovable frontend consumes backend JSON from Railway. This repo should expose the following backend-only endpoints rather than building a duplicate frontend:

- `GET /extraction` returns the cited extraction table for borrower, covenant thresholds, latest-period fields, and a full `monthly_series` for all 24 months. Every citation object includes `document` provenance plus section/line/row metadata and a `confidence` score.
- `GET /covenants` returns deterministic covenant results, breach months, and human-review months with calculated values (`computed_value`, `threshold`, `breached`) separated from interpreted fields (`llm_annotation`, `human_review`). `minimum_liquidity_cash_runway` rows additionally carry `cash_balance_millions`, `cash_floor_threshold`, and `breach_reason` — see §4.1's two-part condition below. These three fields are `null` on every other covenant's rows.
- `GET /memo` returns `model_label`, source-gated memo status, four prose `sections` (`Facility Summary`, `Operating Performance`, `Liquidity & Burn`, `Recommendation`), and a claim-to-source list. Unsupported claims include `source_note: No source — flagged as needs review` and `needs_review: true`.
- `GET /evals` returns summary-card metrics, raw `breach_counts`, field-level `field_accuracy`, `missing_ground_truth` as an empty array once requested field-level fixtures are covered, and prompt/model regression rows for the evals tab.
- `GET /contract` returns all of the above in one mock-contract-compatible document for local frontend wiring.
- `GET /ask?q=<question>` answers a natural-language question against a **fixed set of deterministic lookups** run over the same data `/contract` already serves — no value is recomputed and no LLM determines content. Covers: current ARR/MRR/cash balance/NRR, ARR growth/liquidity-runway/burn-multiple/NRR-floor covenant status, the committed-MRR interpretation, breach months, human-review months, and facility size.
  - Response shape: `{question, matched, lookup, answer, text, sources, message}`.
  - When `matched` is `true`: `answer` carries the deterministic value (plus covenant fields like `threshold`/`breached`/`human_review`/`llm_annotation` where applicable), `text` is a template-generated natural-language sentence built only from that value, `sources` is a non-empty array of `{field, citation, ...}` reusing the exact citation already attached to that field elsewhere in the payload, and `message` is `null`.
  - When `matched` is `false` (the question doesn't match any fixed lookup): `lookup`, `answer` are `null`, `sources` is `[]`, and `message` is a fixed explanatory string. This is the required behavior for anything outside the lookup set — CreditPulse never guesses an answer to a question it can't cite.
- `GET /simulate?months_forward=<int>&arr_growth_pct=<float>&burn_multiple=<float>&start_month=<YYYY-MM>&nrr_pct=<float>` projects covenant status forward from a starting point (`start_month`, default the latest actual month, `2026-12`) under a hypothetical scenario. `months_forward`, `arr_growth_pct`, and `burn_multiple` are required; `start_month` and `nrr_pct` are optional (`nrr_pct` defaults to holding the starting month's actual NRR constant). Returns `400 {error, message}` if a required parameter is missing or non-numeric.
  - Response shape: `{is_simulation: true, start_month, months_forward, overrides, projected_months, breach_months, human_review_months, projected_financials, results}`.
  - `results` has the exact same per-row shape as `/covenants`' `results` (`month`, `covenant`, `computed_value`, `threshold`, `breached`, `citation`, `llm_annotation`, `human_review`) — every threshold and formula in it comes from `covenants.monitor_covenants()` unmodified, never redefined for this endpoint. Two covenants get extra, `/simulate`-only transparency metadata (see below): `net_burn_multiple_cap` rows add `window_fully_projected` and `numerically_settled`; `arr_growth_floor` rows add `comparator_month`, `comparator_is_projected`, and `numerically_settled`. These are purely descriptive of which calendar months feed each covenant's own window/comparator (per `covenants.py`, unmodified) — they never affect `computed_value`, `threshold`, or `breached`.
  - `projected_financials` exposes the hypothetical monthly inputs (`arr_millions`, `mrr_millions`, `gross_burn_millions`, `cash_balance_millions`, `nrr_pct`) the projection is built from, for transparency about the scenario's assumptions — these are constructed, not extracted, and must never be confused with real data downstream. `is_simulation: true` at the top level exists specifically to make that unambiguous.
  - ARR compounds smoothly month over month at the constant rate implied by `arr_growth_pct`, rather than being re-anchored to each specific historical same-month-last-year value — the latter was tried first and rejected because it imported the real dataset's seasonal shape and its deliberate April-2026 ARR-restatement anomaly into an otherwise-constant scenario, producing a discontinuity right at the projection boundary. One consequence: `arr_growth_floor`'s own year-over-year reading (computed by `covenants.py`, unmodified) only exactly equals `arr_growth_pct` once *both* months being compared are inside the projected series (the 12th projected month onward, since its year-ago comparator is the real starting month itself) — before that it's legitimately still dominated by what actually happened historically, the same way a real trailing-twelve-month metric takes a full year to reflect a regime change.
  - `gross_burn_millions` is solved directly from each month's own quarter (`burn_multiple × annualized net-new-ARR ÷ 3`), not chained backward through the previous two months' already-solved burns — the chained form was tried first and rejected because covenants.py's rolling 3-month window makes that recurrence marginally stable with no damping term, so it oscillates without bound once any transient mismatch appears at the historical/projected boundary. The direct form stays smooth and non-oscillating, converging closer to the requested `burn_multiple` as the projection moves away from that boundary.
  - Ratio comparisons in `covenants.py` (`runway`, `arr_growth`, `burn_multiple`) are rounded to 9 decimal places before the breach threshold check, so ordinary floating-point division noise can't push a value sitting exactly at a threshold into a false breach — this applies to `/covenants` too, not just `/simulate`.
  - `window_fully_projected` (on `net_burn_multiple_cap` rows) is `true` once every calendar month in that covenant's 3-month rolling window (this month and the two before it) is itself a projected month, `false` if any of those months is still real history. It is a literal read of month *labels*, not a "has this number settled" signal: a window can be label-pure while still summing a still-elevated value from an earlier projected month whose own construction touched real history (e.g. with a 6-month projection from `2026-12`, month 3's window is label-pure but its `computed_value` is still ~3.4 against a requested burn multiple of 1.5 — see `tests/test_creditpulse.py`'s `test_simulate_burn_multiple_window_fully_projected_flag_matches_window_composition`). Numeric convergence lags window-label purity by roughly one extra month for this reason. The frontend should treat `false` as a hard "transitional" label and treat `true` as "window composition is clean" rather than "value is fully settled."
  - `numerically_settled` (also on `net_burn_multiple_cap` rows) closes that exact gap, using an existing structural fact rather than a numeric convergence tolerance: in `simulate.py`'s `_generate_projected_rows()`, only the *first* projected month can ever have its `net_new_arr` computed against a `quarter_prior[0]` reference that falls strictly before `start_month` — every later projected month's reference is either `start_month` itself (the compounding anchor, not "old" history) or a later projected month, so no other month can carry that kind of boundary contamination. That one affected month's value then sits inside `monitor_covenants()`'s 3-month rolling window for exactly 3 evaluations (itself and the next two), so `numerically_settled` is `true` only once the first projected month has fully rolled out of the window — one evaluation later than `window_fully_projected` alone would suggest. See `test_simulate_numerically_settled_is_false_for_2027_03_true_from_2027_04`, which proves it's `false` at month 3 (`computed_value` ~3.4) and `true` from month 4 onward (`computed_value` within 0.01 of the requested burn multiple).
  - `comparator_is_projected` and `comparator_month` (on `arr_growth_floor` rows) expose the exact calendar month `covenants.py` compares against (12 months back, unmodified) and whether that month is itself projected or real history. For any projection shorter than 13 months every comparator is real history (`comparator_is_projected: false`), which is why `arr_growth_floor` doesn't reflect `arr_growth_pct` alone until the 13th projected month onward (see the smooth-compounding note above).
  - `minimum_liquidity_cash_runway` (loan_agreement.md §4.1, `covenants.py`, unmodified) is a two-part covenant — `cash_balance_millions < 8.0 OR runway < 4.0` — and `computed_value`/`threshold` only ever carried the runway half. Historically the two conditions have always failed together, so `breached` visually agreed with `computed_value < threshold` in `/covenants` by coincidence of the historical data, not because the row exposed the full condition. Under `/simulate`, a burn trajectory that shrinks faster than cash recovers (direct per-month burn solve, see above) can produce a projected month where runway reads comfortably above 4.0 while cash is still below $8M — `breached: true` there is correct (driven by the cash sub-condition), but with only the runway field visible it looks inverted. See `test_simulate_liquidity_covenant_breach_direction_is_not_inverted`.
  - `cash_balance_millions`, `cash_floor_threshold` (always `8.0`), and `breach_reason` close that gap, computed once inside `monitor_covenants()` and shared verbatim by `/covenants` and `/simulate` — not redefined per endpoint. `breach_reason` is `"cash_floor"` when only the cash floor fails, `"runway"` when only runway fails, `"both"` when they fail together (every historical breach month, including `2026-07`, is `"both"`), and `null` when compliant. These three fields are `null` on every other covenant's rows — they're specific to §4.1's two-part structure, not a general-purpose addition to `CovenantResult`. See `test_liquidity_breach_reason_names_which_sub_condition_actually_fired`, which proves `"cash_floor"` for the `/simulate` 2027-02 case (runway compliant, cash non-compliant) and `"both"` for 2027-01 (both non-compliant at once).
  - `numerically_settled` (also on `arr_growth_floor` rows) closes the mirror-image gap to the burn-multiple case above: ARR compounds smoothly starting FROM `start_month`, so `start_month`'s own real ARR is the clean t=0 anchor of the new growth rate, not stale pre-scenario history — a comparator equal to `start_month` reads the new rate just as cleanly as a comparator that's a later projected month does. `comparator_is_projected` is `false` for both cases (`start_month` itself is real, so it's never a member of `projected_months`), which under-reports settling by exactly one month at that boundary. `numerically_settled` is `true` whenever `comparator_month` is `start_month` or later, `false` only when the comparator is genuinely earlier than `start_month`. Example (12-month horizon, `arr_growth_pct=5`, `start_month=2026-12`): month 11's comparator (`2026-11`) is real pre-scenario history and its growth reading is off by >1.0 from the 5% target; month 12's comparator is `start_month` itself (`comparator_is_projected: false`) yet its growth reading is already within 0.01 of 5% (`numerically_settled: true`) — see `test_simulate_arr_growth_numerically_settled_true_at_month_12_despite_comparator_is_projected_false`.
- `GET /sponsor-profile` returns cited founder/executive cards (`role`, `education`, `bio`, `prior_ventures`, each with a `founder_bios.md` citation) plus each founder's `wealth_signal` (`insufficient_data`, `range_low_millions`, `range_high_millions`, `point_estimate_millions`, `confidence`, `methodology_note`, component breakdown, `sources`). No LLM is involved in any wealth number; a founder with no usable disclosed data gets `insufficient_data: true` and null range fields, never a guessed figure.
- `GET /sponsor-network` returns `investor_network.json`'s `nodes`/`edges` as a structured passthrough, plus `edge_type_legend` (label + distinct color/line-style per edge type, for the frontend to render) and `concentration_flags` — investor pairs sharing board seats (`board_seat` edges) across 2+ portfolio companies, computed via set intersection, not an LLM call.
  - Five edge types, each a distinct disclosed fact, never collapsed into one another: `co_founded`, `board_seat`, `invested_in`, `previously_worked_at` (past employment), and `current_role` (presently holds a role at the company, independent of any equity/board disclosure). `current_role` exists specifically so a current non-founder executive with no disclosed cap table stake or board seat — e.g. a recent hire, like Dana Ilkay (CRO, joined 2026, equity grant pending ratification) — still appears connected to Meridian SaaS Co. in the graph rather than showing up as an isolated node. `investor_network.py`'s `find_current_people_disconnected_from_company()` checks this generally (against founder_bios.md's independently-sourced list of who's currently there, not the graph's own claims) — see `test_no_current_person_at_meridian_is_disconnected_from_it_in_the_network` — so the same category of gap (present employment, no disclosed equity/board status) can be caught again if the sponsor module adds more people later.
- `GET /adverse-media` returns cited litigation/regulatory `records` (each with `classification`, `human_review`, `classification_source`, `safety_gate_overrode`, `rationale`) and a `human_review_required_count`. Classification never trusts an LLM or fallback proposal alone — a structural safety gate re-checks each record's own text and forces `ongoing_ambiguous` whenever unresolved language is present, regardless of what was proposed.
- `GET /contract` now also includes a `sponsor` key: `{profile, network, adverse_media}`, the same three payloads above in one document.
- `GET /evals`'s `field_accuracy` now also includes `"Founder Wealth Signal"` and `"Adverse Media Classification"` rows, scored against `data/ground_truth/wealth_estimate_answer_key.json` and `data/ground_truth/adverse_media_answer_key.json` respectively — both authored independently of this module's own code (see the Sponsor & Founder Diligence module section above).
